    Guide

    Working with packman

    Scenarios from simple to advanced. Output marked "captured live" comes from a synthetic demo repository C:\repo\site-demo: SPFx 1.21.1 (apps/news-feed, apps/footer), SPFx 1.18.2 (webparts/team-calendar with the 1.21.1 build toolchain, webparts/people-directory with a TypeScript that does not match its compiler), the libs/ui-kit library and two identical Vite apps tools/vite-*, already linked to the shared store. Every name is invented.

    Key concepts

    Concept What it is
    Workspace The folder packman runs in (the [path] argument, default .). A project is any folder with a package.json down to depth 4; the project id is its relative path with /.
    Stack provider A module that recognizes a framework and checks its rules: npm (every project), spfx, React, TypeScript, Vite, Next.js, Angular, Vue, Electron, ESLint, Jest, Vitest.
    Version group Projects with the same primary stack and version (spfx@1.21.1) and Node major, or a group from policy.groups. Inside a group shared packages should converge on the most common version (policy/group-divergence).
    Baseline The largest group; [baseline] in the output. upgrade moves projects to the newest stack already in the repository by default.
    Policy policy.exactVersions (exact versions instead of ^/~), policy.groups with pins and Node, the repository target, dependency profiles.
    Store .packman/store/<key>: one node_modules installation per group, with the projects linked to it through junctions.
    Verified set Lockfile versions a build passed with (store verify, upgrade --verify), kept in .packman/verified. A deviation from it is npm/unverified-versions.

    Installation and first run

    1. packman itself needs Node 22.12+

      Projects stay on their own Node. The bin/packman.cjs launcher is plain CommonJS and starts on any Node; when the active Node is older than 22.12 it looks for a newer one in nvm-windows, nvm, fnm and Volta and restarts with it.

    2. Build and link

      packman is not published to npm ("private": true), so install it from the repository: 

      git clone https://github.com/vlad-demchyk/package-manager.git
cd package-manager
npm ci
npm run build
npm link

      packman and pm are the same binary.

    3. First check

      check only reads. Without arguments in a regular terminal packman opens the TUI; in CI or with redirected output it runs check.

    4. Configuration (optional)

      packman init creates packman.config.json; --with-groups fills policy.groups with the detected groups and their Node right away. Without the file the defaults apply. Every key is on the Configuration page. 

      packman init --with-groups

    Reading the report

    • x error, !! critical, ! warning, i info; the rule id follows the text (npm/lockfile-drift).
    • Indented lines: evidence (the first 4, all with -v).
    • -> ... [fix-id, risk]: an available fix. fix takes only safe ones by default.
    • Last line: counts by severity. Exit code 1 when there is an error finding or worse (--fail-on).

    Scenario A: one project, no alignment with the others

    When you need to fix one project and leave its neighbours alone, every command takes -p <id> (a glob mask works too). With one selected project the group is that project alone, so cross-project divergence rules (policy/group-divergence) do not fire: packman does not pull the project towards the versions of others.

    1. Check only this project

      --no-security skips the advisories request (fast); --severity error hides warnings without changing the exit code. In the simulator

    2. Fix one rule

      --rule limits fixes to findings with that rule id. Without --apply it is a dry run:

      Fixes with review risk need --risk review:

      To write, add --apply. You get a [y/N] prompt, a backup in .packman/backups/<time>/, a journal entry and a relock of the project when versions changed. In the simulator

    3. Upgrade the stack of one project

      upgrade -p with an explicit --to migrates only that project. The repository target is not written to the configuration in this case (only without -p/-x). Blockers stop --apply and give exit code 1:

      Here webparts/team-calendar moves from 1.18.2 to 1.21.1: runtime packages, the compiler (rush-stack-compiler-4.7 to 5.3 together with extends in tsconfig), ESLint, .nvmrc, .yo-rc.json and a group in the repository policy. There are no blockers, so --apply would write this after [y/N]. A project linked to the store would be a blocker (see the repository plan below).

    4. The lockfile drifted from package.json

      npm/lockfile-drift means npm would pick the versions itself. install does not install such a project; regenerate the lockfile with the project Node first and review the diff in git: 

      packman relock -p apps/news-feed
packman install -p apps/news-feed

      relock runs npm install --package-lock-only --ignore-scripts and does not ask for confirmation. install runs npm ci when there is an npm lock, otherwise npm install, with the project Node, and asks [y/N]. A project linked to the store never runs npm: the line says whether its link is up to date or stale and which command rebuilds the store (install --sync-store does it).

    5. Reinstall from scratch

      packman install -p apps/news-feed --clean   # delete node_modules and the lock, then install
packman clean -p apps/news-feed --modules   # only delete node_modules
packman clean -p apps/news-feed --lock      # only the lockfile

      install --clean deletes nothing when any selected project has no installed Node. Afterwards packman shows the versions that moved away from the verified set.

    6. What is outdated and what is vulnerable

      audit shows only security findings (packages and Node) and returns 1 on critical or error ones: 

      packman outdated -p apps/news-feed
packman audit -p apps/news-feed

    Scenario B: the whole repository

    1. Look at groups and divergence

      = one version everywhere, ≠ divergence (only those with --diverging).

    2. Align

      One package everywhere: the version is the most common one by default, then the highest. packman lists the peer ranges that reject the new version and suggests fix --apply first: here react 17.0.1 from the SPFx projects does not satisfy react-dom@18.3.1 in the Vite apps.

      A package without peer conflicts aligns right away (@pnp/sp to 4.22.0):

      One project after another: without --to packman shows the closest candidates, with --to the differences and the fix:

      --only limits the packages, --pin drops ^/~, --include-missing adds packages the base does not have.

    3. Fix everything that is safe

      Here --risk review included both spfx/align-lockstep and removing unused dependencies (moment in apps/news-feed). Packages referenced only by build configuration (for example, a loader in a gulpfile) can also show up as unused: add those with packman ignore add. Review the diff, then --apply.

    4. Pin the policy

      Groups with Node and pins in policy.groups, exact versions, dependency profiles (profile generate --write, then profile apply). A profile from the current state:

    5. Repository migration

      upgrade without --to moves every project to the newest stack already in the repository; a published release is used only with an explicit --to. The build order and blockers are visible before writing:

      Next: --apply (backs up manifests and lockfiles), --install, --verify (install and build every project), --shared (one installation for the migrated group).

    Scenario C: the shared store

    Identical projects can share one node_modules installation. packman installs it in .packman/store/<key> with the group Node and puts a node_modules junction in the projects.

    1. Plan

      Exact mode groups only projects with identical dependencies and lockfile; here those are the two Vite apps. In exact mode node_modules is one junction for all members, so packman warns about the shared Vite cache:

      Union mode: one installation per group with the union of aligned dependencies; every project keeps its own node_modules folder, so there is no Vite cache warning. For candidates blocked by different versions (versions-differ) packman prints "align first: ..." and the order: check, fix --apply, align --package. For apps/footer it spots a gulpfile webpack rule written against <project>/node_modules: once linked, webpack sees the real path in the store, so the path has to be wrapped in fs.realpathSync(...).

    2. Link

      packman store link --of apps/news-feed --union --replace-existing

      --of finds the current group of a project (keys change with manifests). --replace-existing deletes local node_modules only after the store installed successfully; only manifests and lockfiles are backed up. In union mode project lockfiles are rewritten from the group tree (--no-sync-locks turns that off); such a lockfile works for a plain npm ci in the project, so CI without packman gets the same versions. The store installs from the verified set when there is one (--refresh resolves fresh).

    3. Verify the build

      packman store verify --script buildp   # SPFx: production build with --ship

      Successful builds record verified sets; the next store of the group starts from them. For gulp-based SPFx verify the production build: a script with --ship (buildp in the demo), because build is only a dev bundle. The demo journal shows the link and verify cycle:

    4. Add a package to a linked project

      packman add clsx -p tools/vite-a                      # preview: version, where it comes from, checks
packman add clsx -p tools/vite-a --apply -y --verify build
packman remove clsx -p tools/vite-a --apply -y

      A bare npm install clsx inside a linked project would replace its junctions. add picks the version the group already uses (a pin, the spec of the other members, a profile, the SPFx matrix, otherwise the newest registry version compatible with the group Node and the peers the project resolves) and prints the source. Before writing it checks engines, peer ranges, SPFx lockstep, package families (react/react-dom), runtime singletons and the group: a spec the other members declare differently would split the group, so it stops with the alternatives (take the group's spec, align --package for the whole group, or store unlink and install standalone). With --apply the manifest is written with a backup, the group store is rebuilt from the verified set, every member is relinked and their lockfiles are synced; npm never runs in the projects. --verify builds every member and records the new verified set.

    5. Watch for drift

      stale: package.json changed after linking. drift: npm was run inside a linked project. Both also show up in check (store/link-stale, store/link-drift). packman hooks install adds git hooks that remind you after git pull and branch switches.

    6. Unlink and clean up

      packman store unlink -p apps/news-feed --restore   # remove the junction, restore package.json and lock
packman install -p apps/news-feed                  # get local modules back
packman store prune --trash                        # delete unlinked stores and .packman/trash

      unlink never deletes real folders and does not ask for confirmation; prune asks.

    Scenario D: SharePoint

    Use a dev site only. Components read and write their lists while they run, and seed/clean create and delete lists, columns, items, files, pages, content types and subsites.

    packman never handles passwords or tokens: it opens a browser (Edge or Chrome, with a profile in the packman user folder), you sign in yourself, and packman waits until /_api/web of the site answers 200 (up to 10 minutes). Every REST call runs as fetch inside that signed-in page. --site can be left out when site is set in packman.sharepoint.json.

    1. Collect requirements

      Lists, fields, files and Graph data the components use, from the sources and from the requests of the last sp test:

      --write adds what is missing to packman.sharepoint.json; fill in field types, choices and items by hand (the schema is on the Configuration page).

    2. Seed a dev site

      packman sp seed --site https://contoso.sharepoint.com/sites/dev           # plan
packman sp seed --site https://contoso.sharepoint.com/sites/dev --apply   # create
        planned  list   Events generic
  planned  field  Events.EventDate DateTime
  planned  item   Events: [test] Kick-off
  planned  contentType News Page -> Site Pages add to library
  planned  page   test-news-1.aspx News Page
Dry run: nothing written. Use --apply to create it.

      Illustration from the code and its messages: there is no tenant behind the demo repository. Idempotent: what exists is skipped. A new page is checked out before its columns change; a 423 Locked on that change, and a 500/503 when a fresh content type is added to the library, are retried after 2, 5 and 10 seconds. What was created is recorded in .packman/sharepoint/seeded.json.

    3. Run the components

      packman sp test --site https://contoso.sharepoint.com/sites/dev
packman sp test --properties

      For every SPFx project packman starts the dev server with the project Node: heft start for Heft projects, gulp serve for gulp projects; with both installed, the tool named in the start or serve script wins. Web parts load in the hosted workbench, extensions on a page. Problems are sorted into load, runtime, data, host and known; the component ends ok, needs-data or failed.

      Two fixture keys per component (components.<alias>) change what the browser receives, never the site: properties are laid over the web part's preconfigured properties from the manifest, and page (a site-relative .aspx) hosts the web part in that page's canvas instead of the workbench, so it runs with the real page context. The result line names the page: 

      > apps/news-feed
  ok         NewsFeedWebPart 4 bundles
  needs-data NewsBannerWebPart 4 bundles, https://contoso.sharepoint.com/sites/dev/SitePages/test-news-1.aspx
    data    404 https://contoso.sharepoint.com/sites/dev/_api/web/lists/getByTitle('News')/items

      --properties walks every property pane control of each web part in the workbench (not on pages). Results, logs and screenshots go to .packman/validation/<time>-sharepoint/.

    4. Clean up

      packman sp clean --site https://contoso.sharepoint.com/sites/dev
        page Site Pages: item 12
  contentType 0x0101009D1CB255DA76424F860D91F20E6C4118009A (and its copy on Site Pages)
  list Events (with its items and columns)
  file SiteAssets/footer/contacts.json
Delete what packman created on https://contoso.sharepoint.com/sites/dev? [y/N]

      Prints everything the seed record holds (subsites, pages, content types, items, columns, lists, files, folders), then asks. Without an interactive terminal and without -y it only prints the list. It deletes exactly what seed created; after a clean run without failures the record is empty.

    Scenario E: dry run, --apply, backups, journal, exit codes

    Dry run and --apply

    fix, align, profile apply, upgrade, add, remove and sp seed without --apply only show what they would do. With --apply they ask [y/N]. Without an interactive terminal (CI, pipes, some IDE terminals) the answer is always "no", so -y is needed there. When a file changed between the preview and the write, packman writes nothing and asks you to review the diff again.

    Command Writes without --apply? Asks [y/N]?
    check, list, groups, versions, outdated, audit, node, spfx, store plan, store status no (only check --md) no
    fix, align, profile apply, upgrade, sp seed no yes, with --apply
    install, clean, store link, store prune, sp clean yes yes
    relock, store unlink, store verify, init, ignore add/remove, data update, hooks, log --prune yes no
    profile generate, sp requirements only with --write no

    Backups and the journal

    • Every file is copied to .packman/backups/<time>-<random>/ with its relative path before an edit. To restore, copy the files back or take them from git.
    • Every operation writes a line to .packman/journal.jsonl: packman log (last 30), log -n 5, log --json, log --prune 90.
    • The TUI writes files with backups but does not relock and does not write to the journal: run packman relock after it.
    • After version edits in package.json, fix, align, profile apply and upgrade relock by themselves (--no-relock turns that off).

    Exit codes

    Code When
    0 Success; for check: no findings at the --fail-on level.
    1 check: a finding at the --fail-on level (default error). audit: a critical or error vulnerability. upgrade: blockers. install: a drifted lockfile or no Node. relock, store status --check, sp test: failures. Any refused operation (a message without a stack; the stack with PACKMAN_DEBUG=1).
    2 Invalid packman.config.json (the message names the key).
    npm code install, store verify, upgrade --install/--verify return the code of the failed npm.

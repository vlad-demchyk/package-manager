Troubleshooting

Common problems

The situations come from the messages and errors in the code. Messages are quoted in English (as --lang en prints them). For an unexpected error with a stack trace: PACKMAN_DEBUG=1.

General

"Aborted." although nothing was asked

The confirmation is read from an interactive stdin. Without one (CI, pipes, some IDE terminals) the answer is always "no". Add -y to the commands that ask: fix, align, profile apply, install, clean, store link, store prune, upgrade, sp seed, sp clean.

"Dry run: nothing was written"

Editing commands only show a diff until you add --apply.

"file changed since preview"

The file changed between the preview and the write (an editor or another session). Nothing was written; run the command again and review the new diff.

Exit code 2 and a message about packman.config.json

The file is not valid JSON(C) or fails the schema, for example policy.groups.0.node: invalid Node version or range or target.spfx: target must be an exact version. Fix the named key (Configuration).

"No projects found under <root>"

Check --depth / projects.maxDepth (default 4), include/exclude, requiredFiles, match, -p/-x. Folders starting with . and build folders are not walked; the root is analyzed only with includeRoot: true or when it is the only project.

"packman requires Node >= 22.12 ... no newer installed Node was found"

The launcher needs Node 22.12+ installed through nvm-windows, nvm, fnm or Volta (for example, nvm install 24). The active Node of your shell can stay the one your project needs.

"packman is not built: run npm run build"

The packman folder has no dist/. Run npm run build there.

"npm not found next to <node>"

The Node selected for the project has no npm next to it. Reinstall that Node with its manager.

"(data N days old: packman data update)" in the report

The Node schedule or the Node CVE list is older than 30 days. packman data update writes to the user data folder; bundled files do not change. packman data status shows which copy each check uses.

Lockfiles and installation

"<project>: package-lock.json does not match package.json; run packman relock and review the changes"

install refuses projects with npm/lockfile-drift: an out-of-sync lockfile would let npm pick versions on its own. Run packman relock -p <project>, review the diff (versions that moved away from the verified set are listed), then install. --mode force runs npm install --force when you ask for it.

"N locked versions differ from the set ... last passed with: not verified by a build"

npm/unverified-versions: the lockfile moved away from the versions of the last successful build. When the change is wanted, build again (store verify or upgrade --verify) to record a new set; otherwise restore the lockfile from .packman/backups/ or git.

Lockfiles did not change after the TUI

The TUI writes files with a backup but without relock and journal. Run packman relock for the changed projects.

Node

"No installed Node satisfies ... (recommended ...)" / node/not-installed

The stack ranges, pins, engines, groups or targets have no installed match. Install the recommended version. When engines.node is an exact version nobody has and another installed Node fits the stack, packman fix --rule node/not-installed --risk review offers to put the stack range in engines.node. npm commands skip such projects with exit code 1; install --clean checks every project before deleting anything.

node/pin-conflict

.nvmrc, .node-version, volta, devEngines or a group/target pin does not intersect the stack range. Such a pin is ignored when Node is selected; for .nvmrc and .node-version packman fix --rule node/pin-conflict --apply writes the recommended version.

Shared store

The store and align commands are being refined; the messages below match the current code of the branch.

"Pass --group <key> or --of <project>."

store link needs one of them. packman store plan (or with --union) prints the keys.

"Group ... not found; run packman store plan."

  • Keys change with the manifest, lockfile or Node of any member: packman store link --of <project> --union takes the current group.
  • --union has to match the plan: exact keys come from store plan, union keys (u-...) from store plan --union.
  • A project may be in no group: store plan --union shows candidates with "align first: ...", and --json lists excluded projects with a reason (file:/link:/workspace: dependencies, install scripts, no npm lock v2+ in exact mode).

"real node_modules folders found ...; re-run with --replace-existing"

The members have their own node_modules. --replace-existing deletes them only after the store installed successfully; manifests and lockfiles are backed up, modules are not. store unlink --restore restores the manifests, packman install brings local modules back.

"npm ci failed in <store> (exit N); nothing was linked"

The store installation failed; no project changed. Read the npm output above (for union it is npm install, even though the message says npm ci).

"store ... has dependencies outside their ranges; nothing was linked"

The store tree has broken edges. Align the versions of the listed edges, or relink with --refresh when a verified seed caused it.

"store ... is linked but has no completed installation"

The store folder has no completed installation for this key and Node. Run packman store unlink -p <members> and link again.

stale or drift in store status

  • stale: package.json changed after linking. Run store plan --union, align, then store link --of <project> --union.
  • drift: npm ran inside a linked project (replaced links with copies, added or removed folders). Declare the packages in package.json and relink with --of; npm copies go to .packman/trash.
  • After npm ci the folder is a regular one again: relinking needs --replace-existing.

versions-differ in store plan --union

Shared packages of the group are on different versions. The plan prints an order, and it matters: packman check, then packman fix --apply, then packman align --package <name>. fix first moves the packages whose peer ranges would reject the most common version; if you start with align, it warns "N peer ranges exclude ..." and lists who declares them.

"vite: set cacheDir per project, node_modules/.vite would be shared"

Exact groups only: there the project node_modules is one junction for all members, so the default Vite cache (node_modules/.vite) is shared. Set cacheDir in the vite.config.ts of every project. In union groups node_modules stays a folder of the project, and there is no warning.

"gulpfile.js webpack rule include matches <project>/node_modules"

A gulpfile webpack rule is written against the project's own modules, for example include: path.join(__dirname, 'node_modules', '@pnp'). Webpack follows the junctions to the real path in .packman/store/..., the rule stops matching, and the package is bundled without its loader ("Module parse failed"). Wrap the path: 

include: fs.realpathSync(path.join(__dirname, 'node_modules', '@pnp')),

SPFx production build after linking

store verify runs build by default, which is a dev build. Verify the build that goes to the app catalog: a script with --ship. 

packman store verify --script buildp   # "buildp": "gulp bundle --ship && gulp package-solution --ship"

Can I run npm ci in a linked project

The lockfiles store link writes (union syncs them from the store tree) work for a plain npm ci: CI or a colleague without packman gets the same versions. After such an npm ci the folder is a regular one again and store status shows drift.

Blocker "... is already linked; unlink it before changing its dependency set"

upgrade without --shared does not migrate linked projects. Unlink them or migrate the whole group: upgrade --apply --shared.

SPFx builds

gulp bundle --ship fails on ESLint warnings after an upgrade

typescript-eslint 8 removed rules (ban-types, no-throw-literal, ...) and changed the default caughtErrors from none to all; SPFx --ship fails on warnings unless the gulpfile suppresses them. check reports eslint/unknown-rule and eslint/caught-errors: 

packman fix --rule eslint/unknown-rule eslint/caught-errors --risk review --apply

spfx/tsconfig-compiler

The @microsoft/rush-stack-compiler-* package is right, but tsconfig.json still extends a file of another compiler (typical after an upgrade): 

packman fix --rule spfx/tsconfig-compiler --apply

When the compiler package itself is wrong, spfx/compiler-mismatch fires, and its fix rewrites extends too.

eslint/legacy-config-ignored

ESLint 10 does not read old .eslintrc* files. Move to a flat config by hand or through packman upgrade for SPFx with ESLint 9+.

SharePoint runs

"No SharePoint site: pass --site or set "site""

The dev site URL goes in --site or in packman.sharepoint.json.

"Sign in to <site> in the browser packman opened; waiting..."

Sign in in the window packman opened; it continues as soon as /_api/web answers 200 and stops after 10 minutes. When another Chromium already listens on the debugging port (default 9333), packman attaches to it; for another port use --port.

"Not signed in to <site> within 600 s."

Nobody signed in within 10 minutes. Run the command again and sign in in the packman browser.

"The packman browser does not answer; close it ... and run again."

The browser stopped answering DevTools: one command got no answer in 120 s, or the sign-in probe (15 s each) got none. packman stops instead of hanging. Close the packman browser, or end the msedge/chrome process that uses the packman profile, and run again. The sign-in is kept in the profile.

"No Edge or Chrome found"

Set PACKMAN_BROWSER to the path of a Chromium browser.

"port 4321 is already in use"

Another dev server (gulp serve or heft start) is running. The port comes from the project config/serve.json (default 4321). Stop it and run sp test again.

"gulp serve exited" / "heft start did not start in 300 s"

The dev server crashed or is slow. See <project>-serve.log in the run folder under .packman/validation/. Heft projects run heft start, gulp projects gulp serve; with both installed, the tool named in the start or serve script of package.json is used.

"neither gulp nor heft is installed in the project"

sp test skips projects without an installed gulp or heft. Install the project first.

sp seed: HTTP 423 Locked on a page

A new page is locked for changes until it is checked out. packman checks it out to the signed-in user before it sets the columns and retries a 423 after 2, 5 and 10 s. If the page still fails, it is deleted, so sp seed --apply again creates it anew; only the missing steps run.

sp seed: HTTP 500 or 503 when adding a content type to a library

SharePoint does not see a content type made a moment ago everywhere yet. packman retries after 2, 5 and 10 s before it reports failed. Run sp seed --apply again: the content type now exists and is only added to the library (the dry run shows add to library).

sp clean prints the list and stops

Without an interactive terminal the answer is "no": the list of what would be deleted is printed and nothing is removed. Pass -y. "Nothing to clean." means the seed record for that site is empty.

"properties: the property pane did not open, nothing was checked"

packman could not open the web part property pane (5 attempts). Exit code 1. See the component screenshot.

Exceptions from the workbench or the page

Errors that SharePoint's own bundles raise, including Uncaught (in promise) with a plain value, are classified as host: they never fail a component and are hidden from the text output. summary.json keeps them with the rejected value and up to three stack frames, so you can see where they came from. An exception whose stack points at the dev server is runtime and fails the component.

A data problem keeps failing the run although it comes from the page

Add its text to components.<alias>.known: such problems are reported as known and do not fail the run. Missing lists and fields are needs-data: run sp requirements --write, complete the fixtures, then sp seed --apply.
